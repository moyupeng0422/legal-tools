# 法律问题研究分析 Skill

整合人民法院案例库、国家法律法规数据库两大 MCP，实现多源法律检索与综合分析。

## 模式选择

根据问题复杂度自动选择模式：

| 模式 | 适用场景 | 流程 | 输出 |
|------|---------|------|------|
| Quick | 单一法条查询、简单概念解释、快速确认 | 定向检索 1-2 个数据库 | 直接回答 + 来源 |
| Full | 复杂法律问题、侵权分析、案件研究、法律意见 | 完整五阶段流程 | 结构化研究报告（Obsidian） |

---

## 两大数据源定位

理解每个数据库的特长，才能高效组合检索：

| 数据源 | 核心能力 | 适用场景 |
|--------|---------|---------|
| **国家法律法规数据库** (flk-npc) | 法条原文精确检索 + 命中法条展示 + 高级组合检索 | 定位具体法条、确认法条原文、多条件组合检索 |
| **人民法院案例库** (rmfyalk) | 指导性/参考案例 + 裁判要点 + 统计分析 | 查找典型案例、案例裁判要点、了解案例分布 |

两个数据源互为补充：flk-npc 定位法条原文，rmfyalk 提供权威案例。组合使用形成完整的法律论证链。

## Full 模式工作流程

```
用户提出法律问题
      │
      ▼
[Phase 1] 问题理解与拆解
      │  识别类型 → 提取要素 → 制定检索计划 → 向用户确认方向
      │  ★ 退出机制：非中国法律问题直接终止
      │
      ▼
[Phase 2] 法律依据检索
      │  flk-npc 定位法条原文 + 命中展示
      │
      ▼
[Phase 3] 案例检索
      │  rmfyalk 搜索指导性案例和参考案例
      │
      ▼
[Phase 4] 交叉校验与综合分析
      │  核实法条准确性 → 比对案例裁判要点 → 识别分歧 → [verify] 标记
      │
      ▼
[Phase 5] 报告生成
      加载 references/report-template.md → 填充内容 → 保存
```

### Phase 1：问题理解与拆解

**★ 退出检查**：如果用户的问题不涉及中国法律分析（如纯技术问题、非中国法律、纯事实查询），告知用户本 Skill 不适用并建议正确的工具，不强行进入检索流程。

这一步的目标是确保检索方向正确——方向错了，后面所有检索都是浪费。

**识别问题类型**：法条适用 / 侵权判定 / 权利范围 / 程序问题 / 合同交易 / 其他

**提取关键要素**：
- 涉及的法律领域（知识产权/合同/劳动/公司等）
- 具体法律概念或争议焦点
- 相关主体、行为、标的物
- 时间要素（影响时效性判断）

**制定检索计划**：确定主关键词和补充关键词，选择最可能命中的数据库优先检索。

**输出**：向用户展示问题理解摘要和检索计划，确认方向无误后继续。

---

### Phase 2：法律依据检索

这一步要回答"法律怎么规定的"。先定位核心法条原文，再补充相关法规。

**检索逻辑**：
- 用 flk-npc 做全文检索定位核心法规，再用 `flk_hit_display` 提取命中法条原文——这比人工翻法条快得多，而且保证是现行有效版本
- 对核心法规用 `flk_get_detail` 获取完整结构，理解法条上下文
- 用 `flk_high_search` 做多条件组合检索，精确筛选

**知识产权案件**：加载 `references/ip-strategies.md` 获取预制检索策略。

**关键原则**：
- 法条引用必须来自 MCP 检索结果，不凭记忆引用
- 注意确认法规时效性（`sxx=3` 过滤现行有效）
- 如果关键词没命中，尝试同义词或上位概念

**输出**：立即向用户展示检索到的法律依据清单，标注核心法条和辅助法条。

---

### Phase 3：案例检索

这一步要回答"实践中怎么判的"。法律条文往往概括性强，典型案例能揭示具体适用标准。

**检索逻辑**：
- **rmfyalk_search**：搜索指导性案例和参考案例，获取权威判例

**获取详情**（取最相关的 3-5 个）：
- 对 rmfyalk 结果用 `rmfyalk_get_case` 获取案例详情（裁判要点、裁判理由、关联法条）
- 指导性案例优先级高于参考案例——指导性案例对下级法院有约束力

**输出**：立即向用户展示检索到的典型案例。每条案例须标注来源案例的案号和案例层级（指导性案例/参考案例/一般案例）。

---

### Phase 4：交叉校验与综合分析

这一步确保结论可靠。单源信息可能存在偏差或过时，交叉验证是质量保障的关键。

**过程性校验**（每完成一个争议点分析就检查，不是最后统一检查）：

| 校验项 | 检查时机 | 为什么要校验 |
|--------|---------|------------|
| 法条准确性 | 引用法条后立即核对 MCP 原文 | 记忆中的法条可能与现行版本有出入 |
| 法规时效性 | 引用法条后立即确认 | 引用已废止的法条会导致结论完全错误 |
| 案例层级 | 引用案例时标注 | 指导性案例 > 参考案例 > 一般案例 |

**分析框架**：

综合分析按争议焦点逐一展开，每个争议点严格遵循"争议问题→适用规则→适用分析→结论"结构（即 IRAC 框架）：

1. **争议问题**：该争议点的具体问题是什么
2. **适用规则**：援引法条原文和裁判规则
3. **适用分析**：将规则适用于本案事实，引用具体案例支撑。如有分歧如实呈现
4. **结论**：该争议点的判断，标注确定性

**为什么用这个框架**：这是法律分析的国际标准框架（IRAC，参考 Bloomberg Law, Columbia Law School），确保分析有结构、有依据、有逻辑链，避免跳跃式论证。

**不同观点处理**：对每个争议点，如果存在主流观点和反对观点，必须：
- 分别陈述各自的具体论点、法条依据、案例支撑
- 分析哪个观点更有说服力及原因
- 不选择性只呈现某一面

**[verify] 标记**：无法通过 MCP 确认的内容，用 `[verify]` 标记并说明原因。

### Phase 5：报告生成

加载 `references/report-template.md` 获取完整输出模板。

**关键结构要求**（模板已内置）：
1. **结论先行**：研究问题后紧跟"简要结论"，让读者第一时间获得答案
2. **法条完整引用**：每条法条必须引用完整原文，不得截取片段
3. **案例论理链条**：每个案例必须分析法院的大前提→小前提→推理过程→关键论证
4. **IRAC 结构**：综合分析按争议焦点逐一展开（争议问题→适用规则→适用分析→结论）
5. **实务建议**：结论后附可操作的行动建议
6. **引用来源可跳转**：引用来源表中的每条记录须附详情页链接（利用检索结果中的 ID 构造 URL），方便读者直接跳转查看原文

**文件名格式**：`法律研究-{{主题关键词}}-{{YYYYMMDD}}.md`

保存前确认文件名与用户。

## Quick 模式

当问题简单明确时（如"专利法第X条规定了什么"），跳过完整流程：

1. 确定最匹配的数据库
2. 定向检索
3. 直接回答，附来源引用
4. 不生成完整报告文件

## 端到端示例

**示例 1：专利侵权（Full 模式）**

**Input**：
> 客户生产的一款产品被诉侵犯发明专利权，对方主张等同侵权。请分析等同侵权认定的法律标准和司法实践。

**Process**：
1. Phase 1 识别：侵权判定 > 等同侵权 > 专利法领域
2. Phase 2：`flk_search("专利法")` → `flk_hit_display("等同")` 提取第 59 条
3. Phase 3：`rmfyalk_search(keyword="等同侵权")`
4. Phase 4：按争议焦点分析——"等同侵权的判定标准"→ 适用规则: 法条 → 适用分析: 比对最高法案例"三基本相同+显而易见"标准 → 结论; 如有不同观点如实呈现
5. Phase 5：**结论先行**生成报告 → 简要结论紧跟研究问题 → 法律依据(完整原文) → 案例论理链条 → 综合分析 → 实务建议

**Output 结构**：
```
一、研究问题 + 关键要素
二、简要结论（确定性：中）
三、法律依据（专利法第59条完整原文 + 司法解释）
四、典型案例（含法院论理逻辑链条）
五、综合分析（争议问题→适用规则→适用分析→结论 × 争议焦点 + 不同观点梳理）
六、结论与建议（含实务建议）
```

**示例 2：法条查询（Quick 模式）**

**Input**：
> 商标法第 57 条规定了几种侵权行为？

**Process**：
1. 定向检索：`flk_search("商标法")` → `flk_hit_display(bbbs, "第五十七条")`
2. 直接回答法条原文，标注来源

## 质量校验清单

报告生成后逐项自查：

- [ ] **法条准确性**：所有引用法条均通过 MCP 检索确认，非凭记忆引用
- [ ] **时效性**：引用的法律法规均为现行有效版本
- [ ] **来源标注**：每条法律依据和案例均标注了数据来源
- [ ] **案例层级**：优先引用指导性案例，其次参考案例
- [ ] **不确定标记**：无法确认的内容已用 `[verify]` 标记
- [ ] **问题回应**：报告完整回应了用户提出的所有问题
- [ ] **结论先行**：简要结论紧跟在研究问题之后，读者不需要读完整个报告就能获得答案
- [ ] **法条完整引用**：每条法条引用完整原文，没有截取片段
- [ ] **案例论理链条**：每个案例分析了法院的大前提→小前提→推理过程→关键论证
- [ ] **IRAC 结构**：综合分析中每个争议焦点按"争议问题→适用规则→适用分析→结论"展开
- [ ] **分歧如实呈现**：存在不同观点时，分别陈述并分析哪个更有说服力
- [ ] **实务建议**：结论后附有可操作的行动建议
- [ ] **引用来源可跳转**：引用来源表中每条记录附有详情页链接，读者可直接点击查看原文

## 免责声明

每份研究报告（Full 模式）必须附带以下声明：

> ⚠️ 本报告基于公开法律数据库检索结果生成，受数据库覆盖范围、时效性和检索关键词限制。报告中的法律分析供研究参考，不构成法律意见。具体法律问题请结合案件全部事实和证据，由执业律师出具正式法律意见。

## 工作原则

1. **法条不凭记忆**：所有引用法条必须通过 MCP 检索确认，不依赖记忆中可能过时的内容
2. **多源交叉验证**：关键结论至少有 2 个独立数据源支持，单源信息可能存在偏差
3. **如实呈现分歧**：不同来源对同一问题的观点可能存在分歧，必须如实标注而非选择性引用
4. **标记不确定性**：无法通过 MCP 确认的内容用 `[verify]` 标记，让用户知道哪些需要进一步验证
5. **分层输出**：核心法条和关键案例优先呈现，辅助性内容放在附录或折叠区域
6. **区分事实与判断**：法条原文和案例裁判要点是事实，对法律适用的分析是判断，二者须明确区分

## 认证与异常处理

| 数据源 | 认证方式 | 过期症状 | 处理 |
|--------|---------|---------|------|
| 人民法院案例库 | JWT Token | 返回认证失败 | 提示用户使用 `rmfyalk_set_token` 更新 |
| 国家法律法规数据库 | 无需认证 | — | — |

检索中遇到认证失败时，先告知用户需要更新凭证，不要静默跳过该数据源。
