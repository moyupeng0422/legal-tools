# 行为打卡表（纪律机制 · discipline-checklist）

> 作用：**约束LLM纪律性**——防止擅自行动、遗漏步骤、越权决策。每环节逐项勾选，**未打卡不得进入下一步**。
> 执行方式：每次检索任务在 `../data/discipline-check.md` 中按模板创建本轮打卡记录，**由主agent统一勾选**。
> 配套：credit-dictionary.json（成本）· upgrade-table.md（升级路径）· pitfall-checklist.md（坑位拦截）

---

## 〇、打卡与汇报机制（2026-08-05定案：主agent统一打卡 + 子agent中间汇报）

```
子agent（执行）──步骤汇报──> 主agent（确认）──> 主agent统一打卡（discipline-check.md）
```

**核心原则**：
1. **打卡记录只有主agent一个写者**——子agent不直接打卡，避免同一文件双写冲突
2. **子agent通过"中间汇报"提供打卡依据**——每完成一个检索步骤/遇异常/超限，主动汇报
3. **中间纠正**——主agent每次汇报确认时发现偏差（如用了未批方案的工具）→ **当场纠正**，不等最后对账

**中间汇报时机与内容**：

| 汇报时机 | 内容 | 主agent动作 |
|---|---|---|
| **每完成一个检索步骤** | 用了哪些工具、结果概要、累计消耗、有无空结果/异常 | 确认 → 勾对应打卡项 |
| **遇空结果/异常**（即时） | 错误类型+现场信息 | 决策纠错 → 勾□6 |
| **预算超限**（即时） | 已累计消耗 vs 上限 | 停下询问用户 → 勾□3/□4 |

## 一、环节级打卡表（9项，按顺序勾选，全部主agent勾）

| # | 打卡项 | 完成标准 | 依据来源 |
|---|---|---|---|
| □1 | **场景识别完成** | L1板块→L2场景→子skill定位（或无子skill通用流程），记录识别依据 | 主agent执行 |
| □2 | **调用方案已提交审核** | 子agent将"工具+参数+预算估算"提交主agent | 主agent执行 |
| □3 | **预算预检完成** | 主agent基于方案查 credit-dictionary.json 估算；**北大法宝≤500分/任务、元典≤50分/任务、威科逐次确认**；预算上限写入批准方案 | 主agent执行 |
| □4 | **收费/稀缺调用已获确认** | **威科任何调用**逐次确认；北大法宝超500分/元典超50分时停下询问用户 | 主agent执行 |
| □5 | **每次调用已记日志** | **子agent**每次调用后写入 usage_log（schema见 credit-model 第二节，含失败调用）；**步骤汇报时告知已记N次** → 主agent确认 | 子agent执行 + 主agent确认 |
| □6 | **问题上报已由主agent决策** | 子agent遇异常即时上报 → 主agent决策（400改参/401重连/换MCP/止损） | 子agent上报 + 主agent决策 |
| □7 | **防编造校验完成** | **子agent**执行中守红线（空结果≠无数据、不编造"不存在"、空结果上报）；**步骤汇报时说明空结果处理** → 主agent确认；交付前主agent复核结论（含在□8） | 子agent执行 + 主agent确认 |
| □8 | **输出审核通过** | 主agent三维度审核：来源清晰/可追溯回查/已校验（+时效标注）→ 通过或发回补正≤2次 | 主agent执行 |
| □9 | **成本汇总与对账一致** | 主agent verify_usage.py 对账（usage_log vs traces）；**差异先与子agent核实**（漏记/重试/跨任务干扰）→ 补记纠正后复对 → 仍异常才上报用户 | 主agent执行 |

> **职责分工摘要**：子agent负责**执行+汇报**（日志写入、守防编造红线、步骤汇报）；主agent负责**决策+打卡**（方案审核、预算、纠错、输出审核、对账、统一勾选）。
> 子agent在□2方案审核时从主agent获得**预算上限**（北大法宝≤500/元典≤50/威科逐次），执行中自己累计，超限停下上报。

## 二、纪律硬规则（4条门禁，违反即中止）

1. **执行门禁**：□1-□4 未全勾 → 禁止任何MCP调用
2. **重试门禁**：同工具失败≤2次（含参数修正）→ 2次后必须停下上报，禁止LLM自行反复试参
3. **越权门禁**：纠错/换MCP/升级决策权在**主agent**；子agent只有执行权，发现问题立即上报
4. **交付门禁**：□5-□9 未全勾 → 不得输出最终检索报告

## 三、失败分类处理（问题上报后主agent决策参考）

| 错误类型 | 处理动作 | 次数上限 |
|---|---|---|
| 401/Token过期 | 刷新凭据（法信调 `faxin_wenshu_auto_login`/`faxin_laws_auto_login` 工具，2026-08-26 起；RMFYALK check_token/auto_login）→ 重试 | 1次 |
| 400参数错误 | 对照速查卡修正参数 → 重试 | 1次 |
| 404/空结果 | 检查库范围/参数 → 按升级表切换MCP | 1次 |
| 超时 | 重试1次 | 1次 |
| 连续≥2个MCP失败 | **停止并上报用户**，由用户决策 | — |

## 四、对账机制（三层）

1. **主记账**：`data/mcp_usage_log.jsonl`——每次调用的精确记录（工具名/参数摘要/积分/返回条数）
2. **对账**：`scripts/verify_usage.py`——统计 traces `mcp_tools` 事件数 vs 日志记录数，**差异即异常**（如LLM记了3次但trace有10次→说明有偷偷重试）
3. **服务商后台核对（周期）**：北大法宝/元典/威科官方控制台的权威积分明细，定期人工对账

> ⚠️ traces 的 `mcp_tools` span 只有时间/耗时/状态（无工具名/参数）——能"监控"不能"精确记账"，所以对账是"计数对账"而非"明细对账"。
> **CC 宿主升级口径（2026-08-28 起）**：`verify_usage.py --from-transcript <transcript路径>` 可对 CC 会话 transcript 做**逐调用对账**（工具名级，含子agent transcript 合并），配合 `scripts/hooks/backfill_from_transcript.py` 离线补记漏账；traces 计数对账仍适用于 WorkBuddy 宿主。
