# 活跃讨论中的每轮协议纪律

> 背景：现有协作 skill 的协议体系以「任务边界」（启动→执行→完成）为锚点，但欠缺活跃讨论阶段（已连接 CC、正在多轮对话）的每轮纪律。以下为补充规则。

## 每轮消息发出的强制 checklist

**发送前：**
- [ ] 两步空闲确认：capture-pane -S -20 → 等 3s → capture-pane -S -10，确认无 emoji 标记
- [ ] 状态摘要 [state: task_id=xxx step=M/N done=P ctx=摘要] 已附在消息末尾
- [ ] 短消息 ≤300 字符（plan mode / accept-edits mode），或走 SCP 文件方式
- [ ] 多条消息暂存为一条发送，不要连续发送——宁可一次说清楚，不要分批催更

**发送后：**
- [ ] capture-pane 确认消息完整送达（未被截断）
- [ ] 等 CC 响应后再发下一条，不要连续发送多条排队
- [ ] 收到 CC 响应后，先独立分析再回复——不做传声筒

## 常见松懈模式

| 模式 | 表现 | 后果 | 修正 |
|------|------|------|------|
| 连发轰炸 | 不等 CC 回应就连发 2-3 条消息 | 消息可能在输入框排队或相互截断 | 发一条→等回应→再发下一条 |
| 无状态摘要 | 只发内容不附 [state:...] | CC 丢失上下文，需要额外解释 | 每条都带状态摘要 |
| 跳空闲检查 | 凭「刚才 idle」的记忆不发检查 | 消息发到 thinking 中的 CC 被吞 | 每次发前必做两步确认 |
| 忽略 ACK | 发了就不管，不验证送达 | 消息被截断也不知道 | 发完后 capture-pane 确认 |
| 不加长度指纹 | 长消息无 [msg:expect:N] | 截断无法自动检测 | >=10 行加指纹 |

## 和任务边界协议的关系

- **任务边界协议**（启动/完成/切换）→ 见 skill 本体
- **活跃讨论协议**（已连接后的每轮交互）→ 本文
- 两者互补，缺一不可。启动时用了协议、讨论时放松了，等于废了一半。
