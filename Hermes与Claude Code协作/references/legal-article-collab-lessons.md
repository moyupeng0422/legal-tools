## 社媒写作协作流程（2026-06-09）

**来源**：用户要求 CC 用社媒写作 skill 撰写公众号文章介绍协作经验。

**完整流程**：
```
1. Hermes 在云端写好素材/要求文件
2. SCP 到 CC 本地：scp brief.md <host-alias>:"C:/Users/用户名/brief.md"
3. 启动 CC（六步法）→ 发短指令引导：
   - "读取 C:\Users\用户名\brief.md"
   - "进入 D:\claude vscode\法律相关skill自研仓库\社媒写作"
   - "加载 SKILL.md，用 /style-write Full Mode"
4. CC 自主加载 STYLE.md + 参考资料 → 写入本地 draft.md
5. Hermes SCP 拉回：scp <host-alias>:"C:/Users/用户名/draft.md" /tmp/
6. Hermes 独立审查 → 发修改意见回 CC 或给用户
```

**关键点**：
- 素材走 SCP 文件，不走 tmux 消息（长素材在 plan mode/accept-edits 下必截断）
- 社媒写作 skill 路径：`D:\claude vscode\法律相关skill自研仓库\社媒写作\`
- CC 在 plan mode 下写文件被 PreToolUse:Write hook 拦截 → 需切 accept edits 模式
- CC 自动运行 6 门去 AI 味检查 + 10 项质量自检清单，Hermes 不需重复

**实测结果**：CC 产出 160 行约 2800 字文章，AI 味 3%，口语化密度 0.55，平均句长 22 字。风格匹配良好。

### CC 侧配合文档同步

云端协作 skill 更新后，CC 侧的 `.claude/rules/hermes-collab.md` **不会自动同步**。涉及协议变更（如新增六步法、检查 #-1）时，需手动同步。

CC 侧文档路径：`D:\claude vscode\.claude\rules\hermes-collab.md`

同步方式：通过 CC session 直接 Edit，或 SCP 新版后让 CC 替换。

## 3. CC常见问题及应对

### 3.1 修正时重写全文（最严重问题）

**症状**：要求CC修正反法条号（"第九条"→"第十条"），CC重写了全文→将《规定》自身条款编号全部搞错（Art.9保密措施→Art.6）。

**应对**：指令中明确写"**仅修正XX，保持文章结构、内容、其他条款编号不变。不要重写全文。**"

**触发次数**：本次任务中触发2次。

### 3.2 法律条款编号双重核对

**要点**：审核时必须同时验证上位法（反法条号）和下位法（《规定》条号）。

**flk-npc陷阱**："命中展示"不返回条号，不能用它验证条号。替代方案：新旧对照表或官方全文。

### 3.3 CC陷入工具死循环

**症状**：CC反复运行相同Python脚本从对话历史中查找文章。

**应对**：Ctrl+C中断 → 发送简短指令打破循环（"停止。不要搜对话历史。用你的知识重新输出。"）

### 3.4 社媒写作技能：读取≠应用

**症状**：CC读取了社媒写作技能文件（`CLAUDE.local.md`，57行），但输出仍是教科书式逐条翻译。

**根因**：CC读取技能文件只是"知道了"，但没有将它内化为写作风格。

**应对**：必须同时提供：
1. 参考文件路径（对标风格）
2. 具体风格要求清单（结构/语言/排版/实务导向）
3. 明确写出"不要教科书腔，要有律师视角"

## 5. tmux操作经验

### 5.1 paste-buffer污染问题

**症状**：paste-buffer发送的消息混入capture-pane中的残留表格/代码。

**应对**：paste-buffer前必须 `tmux delete-buffer -t claude-session -b 0`。

### 5.2 发送方式选择

- **正常模式**（无⏸/⏵⏵标记）：paste-buffer 一次性发送500-2000字符可靠
- **plan/accept-edits模式**：必须分段短send-keys（每条<300字符，间隔1-2s）
- 超过2000字符：SCP文件到Windows后让CC读取

### 5.3 accept edits阻塞

"accept edits on"状态下所有输入被视为编辑。Escape在tmux中不可靠。可靠方案：Ctrl+C → 等1s → 重新发指令。

## 6. 方向纠正（V3→V4 循环的根因）

### 6.1 最严重问题：文章方向根本错误

**V3 症状**：CC 输出的是"《规定》vs 旧规（1995年41号令）"对比文章（标题「八大核心变化」）。

**用户纠正**："不是要让新规定与旧规定进行比对，而是要讲新规定与新修订的反不正当竞争法是怎么配合和补充的。新修订的反不正当竞争法肯定也有独特之处，那么新规定是怎么处理这些独特之处。"

**根因**：Hermes 的 V3 指令虽然写了"反法×规定"，但措辞不够精确，CC 理解成了"新旧对比"。

**修正后的正确框架**：
```
反法新突破①：第10条扩大侵权类型
→《规定》第13-14条如何落地：教唆4形态/第三人判断框架
→ 配合关系

反法新突破②：第39条举证责任转移
→《规定》第20条如何创新：行政程序首创推定规则
→ 补充关系

反法未覆盖→《规定》独立补充：认定标准(第5-9条)、保密措施清单(第9条)、
  合法例外(第15条)、完整行政程序(第17-23条)
```

**关键教训**：V4 指令必须明确写出"配合一/二/三"和"补充一/二/三"的分块框架，不能只说"配合与补充关系"这种模糊措辞。CC 需要看到具体的对应逻辑链（反法哪条→《规定》哪条→什么关系）。

### 6.2 上下文窗口饱和终止

**症状**：CC 反复自动压缩（4+次），读取相同文件后仍无法进入分析，最终卡在"Dilly-dallying"状态。

**根因**：多轮辩论 + 多版文章（V1/V2/V3/正式版）+ 风格分析表格 + 保活脚本输出，累计远超 CC glm-5-turbo 上下文窗口。

**应对优先级**：
1. `/clear` 重置会话（最快）
2. Print Mode (`-p`) 一次性任务
3. 不要再发任何新指令给旧会话——只会触发更多压缩

**预防**：法律文章协作最多保留 **2 轮修正**，超过则 `/clear` 重建会话。

### 7.1 /clear → 激活四步法 → R1→R2→R3 全流程

```
R2质询微调结构 → CC逐条核实条款编号 → R3定稿输出（5200字218行）
```

**成功要素**：
- 新会话干净上下文，CC 响应速度正常
- 按 Pitfall #75 执行：R1 只发原始材料（文章链接 + 参考文件 + V3问题 + 用户要求）
- CC 独立分析提交了完整的 R1（文章定位+八节结构+三层配合关系+与V3差异表）
- R2 质询仅需微调（第七节并入导语、第八节升级独立章节）
- R3 输出前 CC 主动逐一核实 17 个条款编号 + 确认 Art.20"实质相同"非"推定"

### 7.2 CC 写入文件替代对话输出（新发现）

**行为模式**：CC 在 accept-edits 阻塞时，会将分析/草稿写入本地文件而非输出到对话。本次 CC 将 R1 分析写入了 `商业秘密保护规定深度解读_R1.md`。

**应对**：
1. 如果 CC 长时间"thinking"但无对话输出 → 检查是否有新文件写入磁盘
2. 用短指令让 CC "展示文件核心结论"
3. **不要等 CC 在对话中输出** — 它可能永远卡在 accept-edits 上

### 7.3 CC 框架默认化倾向（新发现）

**症状**：CC 在 R1 中明确同意"反法×规定配合关系"方向，但写到文件时仍使用了"新旧对照：八大核心变化"作为章节标题——回到了它最熟悉的新旧对比框架。

**根因**：CC 的"知道方向"和"实际写作"之间存在脱节——口头同意不等于写作遵从。

**应对**：
- R1 阶段 CC 写入文件后，Hermes 必须读取文件确认方向一致
- R2 不只要讨论结构，还要**锁定章节标题措辞**（如"本节标题不得出现'新旧''变化'字样"）
- R3 指令中追加"检查全文章节标题，不得出现'新旧对比''八大变化'等指向41号令的表述"

### 7.4 Rename 串字问题

**症状**：`<!-- HERMES-ACTIVATE -->` 后立即跟 `/rename` + 背景消息，CC 把后续文字也吃进了 rename 参数（session 名变成"商业秘密规定解读R1背景：用户是中国知识产权律师..."）。

**应对**：HERMES-ACTIVATE 和 rename 之间至少等 2 秒；rename 执行后 capture-pane 确认名称，C-c 清空残留再发下一条。

## 8. 文章内容风格偏好（2026-06-09 用户新增）

**触发场景**：CC 产出的社媒写作文章（AI 协作经验分享），用户审查后提出两条核心反馈。

**偏好 1：视觉元素密度要高**
- 用户原话："文字内容太多了，表格，代码块，流程图还不够丰富"
- **规则**：公众号文章不能是纯文字堆砌。每 300-400 字应穿插至少一个视觉元素（表格/代码块/流程图/ASCII图/对比栏）
- 视觉元素类型优先级：对比表格 > 流程图/架构图 > 代码块 > ASCII 示意图 > 引用块
- 纯文字段落连续不超过 3 段（约 500 字），之后必须有图表或结构化元素打断

**偏好 2：选题必须多样化，拒绝重复框架**
- 用户原话："又是踩坑，每次都发踩坑有点太重复了"
- **规则**：公众号已发过的选题框架/角度不应重复使用。发新文章前应检索确认与已有文章不重复
- "踩坑/避坑"是典型已过度使用的框架——虽有效但已审美疲劳，应寻找新鲜切入点
- 替代角度示例（CC 提供）：正面案例 walkthrough、管理视角（给 AI 写员工手册）、体验向（手机遥控 AI）
- **Hermes 审查 CC 选题时的检查项**：(a) 与近 3 个月公众号文章角度是否重复 (b) 是否有更具新意的切入点 (c) 视觉元素是否足够丰富

**对 CC 社媒写作 skill 的影响**：以上偏好应同步到 CC 本地的社媒写作 skill（`D:\claude vscode\法律相关skill自研仓库\社媒写作\STYLE.md`），特别是视觉元素密度要求。可通过 CC session 直接 Edit 同步。

## 10. 续篇文章写作模式（2026-06-09 实战）

**背景**：用户要求写一篇公众号文章，作为之前「配置 Hermes 云端 + 远程指挥 CC」文章的续篇。本节记录续篇写作的协作教训。

### 10.1 续篇叙事结构

续篇文章的叙事线应遵循：**承上 → 问题暴露 → 设计解决 → 展示结构 → 分享**

| 环节 | 内容 | 注意 |
|------|------|------|
| 承上 | 简短回顾上篇（1-2句），建立叙事连续性 | 不重复上篇的技术细节 |
| 问题 | 实际使用中暴露的具体问题（列表/表格） | 问题必须是真实的，有具体案例支撑 |
| 设计 | 讨论/决定用什么方案解决问题 | 可以简单提及决策过程 |
| 展示 | 把方案/工具的结构摆出来，逐一解释每个部分解决什么问题 | **核心章节，占比最大** |
| 分享 | 开源/可用 + 获取方式 + 邀请反馈 | 行动式结尾，不是感受式 |

### 10.2 "架构/结构"章节写什么

**用户纠正**：CC 在大纲中把"架构概览"写成 Hermes↔SSH↔tmux↔CC 的远程部署架构图——这是上篇已经讲过的内容，续篇不应重复。

**正确做法**：续篇的"结构"章节应展示**工具/方案本身的文件结构**（目录树 + 各文件职责说明），而非部署拓扑。例如：
```text
Skill 端（云端）
├── SKILL.md                 ← 主文件
└── references/
    ├── message-protocol.md
    └── debate-rules.md

CC 端（本地）
└── .claude/rules/
    └── hermes-collab.md    ← CC 自动加载
```

**判断标准**：如果"架构"内容在上篇文章中已经覆盖，续篇必须换角度——展示方案内部的组件结构、设计逻辑、每个部分解决什么问题。

### 10.3 锁定用户方向，不要让 CC 自由发挥选题

**错误模式**：用户给出了明确的续篇方向（"之前配置好了，使用中发现问题，用 skill 规范解决，展示 skill 结构，最后分享"），但 Hermes 只给 CC 发了一个模糊的 brief（"写一篇关于 AI 协作经验的公众号文章"），导致 CC 提出了三个完全不相关的选题方向（正面案例 walkthrough / 给 AI 写员工手册 / 手机遥控 AI）。

**正确做法**：当用户给出了明确的文章方向和叙事线时，Hermes 应将用户原话（或精确提炼后的方向）**原样写入 brief 传给 CC**，而不是让 CC propose 新方向。Brief 中应包含：
1. 用户指定的叙事主线
2. 各章节的大致内容要求
3. 用户指定的结构/架构章节该写什么
4. 结尾要求

### 10.4 Hermes 必须审查 CC 的选题/大纲是否符合用户意图

**错误模式**：CC 提出了三个方向 A/B/C，Hermes 直接转发给用户选择——但三个方向都完全偏离了用户之前明确表达过的写作意图。Hermes 作为中间人应先比对 CC 提案与用户原始意图的匹配度。

**正确做法**：收到 CC 的选题/大纲后，Hermes 应先做匹配度检查：
- CC 提案是否符合用户之前明确表达的方向？
- 如果偏离，Hermes 应指出偏差并提供修正建议，而不是把完全偏离的方案发给用户
- 只有当 CC 提案确实与用户意图吻合但有多个合理变体时，才转发给用户做最终选择

**反面案例（本次）**：用户明确说"续篇，展示 skill 结构，逐一解释"，CC 却提出了"手机遥控 AI 敲代码"这种完全无关的方向，Hermes 未加审核直接转发。

## 11. 用户偏好总结（更新）

1. 写作风格：律师视角 > 教科书式解读；双视角实务 > 单方面分析
2. 协作纪律：CC独立分析在前，Hermes消化在后；R1只发原始材料
3. 纠错方式：发现问题立即打断，不等CC完成一轮再说；用「停止。不要X。改为Y。」句式
4. 条款编号：逐条双向核对，不接受任何模糊；flk-npc「命中展示」不返回条号，不可用于验证
5. 写文章：必须给参考对标文件 + 具体风格要求 + 明确方向框架（配合X/补充X，不要模糊措辞）
6. 方向敏感：用户说「跟XX挂钩」「怎么配合和补充」时，文章主线必须是两者互动关系，不能偷换成新旧对比
7. 社媒技能：CC读取技能文件不等于应用风格；必须同时给参考文件路径 + 具体风格清单
