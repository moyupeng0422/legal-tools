## DONE [TASK_MAP] 块格式

```
<!-- DONE:task-X:step-N -->
[STATUS]
  result: pass
  verified: true
  ...
[TASK_MAP]
  task_id: test-003
  step: 3/3
  session: v3协议压力测试与14问题验证
  timestamp: 2026-06-01T14:30:00+08:00
[/TASK_MAP]
[/STATUS]
<!-- /DONE -->
```

Hermes 解析：`\[TASK_MAP\](.*?)\[/TASK_MAP\]` 正则提取 → 键值对解析 → 写入 `claude_task_map.json`。

## 关键教训

1. **/rename 后立即写 task_map**，不等任务完成——上下文被压缩后记录必然丢失。
2. **Paste-buffer 截断是真实风险**：本次讨论中 Q1-Q3 就被截断，CC 只收到 Q4-Q5。
3. **状态摘要不写就不能发**：Hermes 侧发送前自检是最后一道防线。
4. **Checklist 不是建议是纪律**：标题「强制执行，不可跳过」要当真。
5. **CC 无法直写云端文件**：所有云端持久化由 Hermes 侧完成，CC 只输出结构化数据。

## 2026-06-09 自查 — CC 协作写公众号文章

> 自查触发：用户要求 CC 基于协作 skill 写公众号文章，Hermes 审核 CC 产出后做 R1 辩论。

### 发现问题

| # | 问题 | 说明 | 严重度 |
|---|------|------|--------|
| 1 | **CC 倾向"文档翻译"而非叙事** | CC 的文章结构方案本质是"规范逐条翻译成中文"，只是换了组织方式。读者不关心每条规则的模板长什么样，他们关心"为什么要这样设计" | 高 |

### R1 修正方向（Hermes → CC）

- 总字数控制在 4000-4500 字
- 按消息生命周期组织是对的，但每章只选 1-2 个最有意思的机制深入讲，其余一句话带过
- 增加"为什么这样设计"的设计动机叙事，减少模板罗列
- CC 端 rule 章节聚焦 3 个亮点：协作身份定义（CC 不是客服）、拒绝权（AI 可以拒绝指令）、降级规则（3 次不遵守就放弃）

### 关键教训

9. **CC 写技术文章的天然倾向是"翻译文档"**：Hermes 的 R1 必须主动检测"规范逐条翻译"模式并纠正为叙事驱动。判别信号：文章结构按规范编号平铺、每条都展示模板全文、缺少"为什么这样设计"的段落。
10. **字数是硬约束**：微信公众号技术文 4500 字是红线，超出阅读完成率暴跌。R1 审核必须估算字数。
11. **给 CC 的修正指令必须精确描述问题本质，不能只描述表面症状**：本次 CC 写了虚构的文件名（message-protocol.md 等不存在），Hermes 说"缩进不对"（只看到了 `│` 缺失），CC 按字面意思只修了前缀，文件名虚构问题完全没动。正确做法：先自己定位清楚"文件名是虚构的"这个根因，再精确指令"文件名全部错了，替换为真实文件名 X/Y/Z"。教训：CC 不会读你的心，你描述什么它就修什么。
12. **审核 CC 产出时必须事实核查所有具体技术细节**：文件名、路径、命令、数据——不能只审内容逻辑和叙事结构。Hermes 手握 find 结果（24 个实际文件列表）却未对照文章中的目录树，导致 3 个虚构文件名通过审核。审核清单：先拿实际数据源（文件系统、配置、日志）与文中具体细节逐项比对，再评价叙事质量。

### 根因诊断（CC 接受）

**CC 把协议视为"可选附加"而非"基础约束"**。CC 认为"改对文件=做对了"，标记输出是锦上添花。实际上对 Hermes 来说，结构化标记是 programmatic 判断 CC 状态的唯一基础设施，没有它协作退化成"一个 AI 给另一个 AI 发微信"。

CC 原话（R2）："协议执行的可靠性不取决于规则写得多详细、模板设计得多精巧，而取决于执行方是否真正把协议视为不可跳过的约束。"

### 关键教训

15. **审计 CC 合规性时必须让 CC 自查**：用户纠正"会不会是 CC 遵守了，但是你没发现"。capture-pane 滚动截断可能导致 Hermes 漏检。正确做法：先让 CC 自查输出过哪些标记 → 再与 Hermes 侧观察对照 → 差异点追问。
16. **CC context 文件自动加载 ≠ CC 会遵守**：`.claude/rules/hermes-collab.md` 是 session 级自动加载的，不依赖激活标记。CC "协议未触发"的借口不成立——问题在 CC 优先级判断，不在机制设计。
17. **协议设计中"惩罚提醒者"的逻辑有缺陷**：降级规则（连续 3 次不遵守→停止提醒）实质上惩罚了 Hermes（停止发送标记），而非 CC（停止违规）。CC 自己指出了这个双刃剑效应。
18. **认知负担是真实约束**：ACK 指纹 + DONE 三层嵌套 + PAUSE 四字段，对 LLM 来说过于复杂。简化方向：ACK 只需 task_id，DONE 只需结果摘要，去掉 STATUS/CHECKLIST/TASK_MAP 嵌套。越简单越容易被遵守。
19. **审计结论不可以偏概全**：Hermes 基于"短对话/讨论类任务"的观察推出"几乎全部零实操"结论，用户以 wechat-fix 多步骤任务的反例推翻。正确做法：审计前先按任务类型分类采样，再给分档结论（高/中/零），避免全称量词。教训：用户说"会不会是 CC 遵守了但没发现"时，应立即自查而非坚持己见——用户日常观察频率 > Hermes 间歇性审计。
20. **用户纠正证据优先于 Hermes 分析结论**：用户出示具体 DONE 输出作为证据，Hermes 应接受而非辩护。用户日常观察 CC 产出频率远高于 Hermes 单次审计，对遵守率的判断更可靠。
