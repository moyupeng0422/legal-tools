# Reference: 设计讨论方法论

当需要与 CC 协作讨论设计/架构方案时，遵循独立分析-辩论-收敛-实现的流程。

## 为什么需要方法论

反面案例 2026-06-17 实战：Hermes 直接命令 CC 产出完整方案，跳过了独立分析和辩论环节。结果：CC 产出了范围膨胀的方案引入不必要的 MCP 依赖，Hermes 只能事后质疑修正，浪费 CC API 消耗 $1.56/10turns，违反了协作协议的质疑优先和不传话原则。

## 正确流程 三阶段

### 阶段一 各自独立分析

1. Hermes 先做自己的分析 用 web_search read_file 等工具独立研究问题空间形成初步判断
2. 向 CC 发送讨论提示 不是任务指令 用自然语言不使用 TASK 格式明确说请先独立分析
3. 提示中应包含 背景信息 需讨论的问题清单 明确禁止不要直接出完整方案不要修改文件咱们先讨论

### 阶段二 辩论对齐

1. Hermes 独立审视 CC 的输出 按协作协议质疑优先原则找问题找盲点
2. 发质疑给 CC 具体 有据可依的质疑点不是泛泛而谈
3. CC 逐点回应 同意 反驳 修正
4. 可能需要 2-3 轮辩论 直到双方达成共识

常见需要质疑的点：
- 范围是否膨胀 偏离用户原始需求
- 复杂度是否过度 用户偏好够用就行
- 架构决策的 trade-off 是否被充分讨论
- CC 是否引入了不必要的依赖

### 阶段三 收敛到实现

1. 确认共识点 用简洁的表格或清单汇总双方同意的方案
2. 向用户汇报 附 CC 的分析摘要标注有分歧的点
3. 用户确认后 才进入实现阶段 写文件 执行命令
4. 发实现指令给 CC 此时才发 TASK 格式或明确命令

## 关键区分 讨论 vs 任务

讨论模式：自然语言消息 CC 做独立分析师 Hermes 做质疑者 产出共识方案 禁止修改文件
任务模式：TASK 结构化指令 CC 做执行者 Hermes 做监督者 产出代码文件

## 与协作协议的关联

遵循质疑优先 SKILL.md 核心原则 辩论阶段是此原则的实践
遵循不传话 Hermes 不是简单转发用户需求给 CC 而是先形成自己的分析
遵循步数小于等于3 讨论阶段每个 Hermes 到 CC 消息不超过 3 个核心问题
