## 1. 监控链路

每次 send-keys / paste-buffer 后，必须执行监控循环。不允许"发送后不管"。

```
send-keys / paste-buffer
       │
       ▼
  轮询循环（间隔 5-8 秒，前 30s 高频）
       │
       ▼
  capture-pane → 三区域解析（§2）
       │
       ├─ 区域① emoji（✶/✽/✻）→ CC thinking → 继续轮询
       ├─ 区域中 ● 开头行 → 工具调用中 → 继续轮询
       │
       ├─ 区域① 无 emoji → CC 空闲
       │    ├─ 权限弹窗 → 按两拍法处理
       │    ├─ CC 提问 → 进入裁决（§4 辩论协议）
       │    ├─ DISCUSS 排队 + CC 执行中 → C-c 打断（§9）
       │    ├─ 任务完成 → 提取 [TASK_MAP] → 记录 task_map → 进入事实校验
       │    └─ 需确认的操作 → 提交用户确认
       │
       ├─ PAUSE 标记 → CC 需要决策，按 §8 PAUSE 处理
       │
       ├─ Error / FAILED / Exception → 进入错误恢复
       │
       └─ 连续 3 次输出相同（非 thinking）→ 判定 session 状态（可能是弹窗滞后）
```

**COMPLETE 确认流程：**

```
task 最后一步 DONE → Hermes 发 <!-- COMPLETE:task-X --> → CC 回复确认 → task 终止
```

## 2. CC Pane 三区域模型

capture-pane 捕获的是 CC 整个终端画面，需区分三个独立区域：

```
区域① → ✶ Cascading… / ✻ Churned for 40s / · Hyperspacing…
          ↑ 输入框上方 · thinking 指示器（emoji + 文字）
区域② → > 或 ❯
          ↑ 输入框 · 提示符
区域③ → ⏸ plan mode on / ⏵⏵ accept edits on / （无标记）
          ↑ 底部状态栏 · UI 模式
```

**关键规则：**
- **空闲判断只看区域①**：有 emoji（✶/✽/✻/✢/· 等）= thinking，无 emoji = 空闲
- **区域③ 只影响发送方式**：accept edits 用短 send-keys 不用 paste-buffer，但不影响是否可发指令
- **不要混淆**：区域①（thinking 指示器）≠ 区域中的 `●`（工具调用行首标记），两者都是"忙碌"信号但来源不同

**⚠️ 快照滞后陷阱（2026-06-02 教训）：**

capture-pane 只捕获当前可见区域，可能包含 **过期的 thinking 残留文本**。典型场景：
1. Hermes 发指令 → sleep 30s → capture-pane 看到 `✻ Topsy-turvying…`
2. 判定"CC 还在 thinking"→ 继续等待
3. 实际上 CC 只思考了 10s 就出了 plan，已经弹窗停在 `Would you like to proceed?` 等了 20s

**根因**：CC 的 thinking 文本留在 scrollback 中，pane 没有滚动到最新位置时，capture-pane 抓到的仍是旧内容。

**防范**：
- **前 30s 高频检查**：发指令后前 30s 是弹窗/plan 高频出现期，间隔不超过 8s
- **用 `-S -5` 快速确认最新状态**：比 `-S -20` 更不容易抓到 scrollback 中的旧 thinking 文本
- **发现 thinking 标记时仍要扫一眼底部**：如果 thinking 标记旁边出现 `Would you like to proceed?` / `Enter to select` / `ready to execute`，说明 CC 已经停了
- **连续 2 次 capture-pane 输出相同但未变化**：可能不是 thinking 而是弹窗——加大 `-S` 行数确认

## 2.5 R1 独立分析汇报格式（2026-06-16 新增）

当 CC 产出详细的审阅/分析意见后，Hermes 的 R1 汇报应使用结构化表格格式，让用户一目了然地看到每条建议的裁决。**这是「不传话」原则的具体呈现形式。**

**格式模板：**

```
CC 审阅意见汇报（Hermes R1 分析）

| CC建议 | 我的判断 |
|--------|---------|
| 具体建议内容 | ✅ **采纳** — 理由 |
| 具体建议内容 | ❌ **不采纳** — 理由 |
| 具体建议内容 | ⚠️ **质疑** — 具体质疑点 |
| 具体建议内容 | ⏸️ **暂缓** — 原因 |
| 具体建议内容 | ✅ **采纳（但CC误读）** — 纠正说明 |

---

**总结：采纳 N 项，质疑 N 项，不采纳 N 项，暂缓 N 项。**
```

**关键规则：**
- 每条都必须标注 **✅采纳 / ❌不采纳 / ⚠️质疑 / ⏸️暂缓**，不留未评判的条目
- 每条裁决都附**理由**——"我同意/不同意因为..."
- CC 误读了方案内容时，标注"CC 误读"并说明实际情况（如方案中已经包含但CC以为缺失）
- **不要**只列出 CC 的意见让用户自己选——这是传声筒行为
- 表格后附一句数字总结（采纳/质疑/不采纳/暂缓各几项）

## 3. 状态判定表

| 区域 | 指示符 | 含义 | Hermes 应对 |
|------|--------|------|-------------|
| ① | `✶`/`✽`/`✻`/`✢`/`·` + 文字 | CC 正在 thinking | 继续轮询，不中断 |
| ① | 无 emoji | CC 空闲 | 可发指令（用合适的发送方式） |
| — | `❯` / `>` | 输入提示符，等待输入 | 发任务 / 处理弹窗 / 读结果 |
| — | `●` 开头的行 | CC 正在执行工具调用 | 继续轮询，不中断 |
| `◐ medium · /effort` | 当前推理深度 | 信息性，不处理 |
| `ctrl+o to expand` | 工具输出被截断 | 可选 Ctrl+O 展开详情 |
| `Allow Claude to ...` | 工具权限请求 | 按弹窗 2 处理 |
| `Error` / `FAILED` / `Exception` | 执行出错 | 触发错误恢复 |
| `rate_limit` / `overloaded` | API 限流 | 触发限流恢复 |
| `billing_error` | 计费问题 | 汇报用户 |
| `Enter to select` | **CC interview 表单** | 按数字键选择（§session-lifecycle） |
| `Skip interview` | **CC interview 表单** | 直接立即结束 interview |
| `Would you like to proceed?` | CC 等待确认执行 | 判断后回复 Yes/No/修改 |
| `ready to execute` / `plan and is ready` | CC plan 完成待审批 | 审查方案后决定 |
| `<!-- PAUSE:task-X:step-N -->` | CC 需要 Hermes 决策（v2.1） | 按 §8 PAUSE 处理 |
| `<!-- COMPLETE:task-X -->` | Hermes 发送的 task 完成标记（v2.1） | CC 回复确认后 task 终止 |

**轮询命令：**

```bash
# 基础（最后 20 行）
tmux capture-pane -t claude-session -p -S -20

# 详细（最后 60 行，读取完整输出）
tmux capture-pane -t claude-session -p -S -60

# 快速检查（最后 5 行，判断空闲/忙碌）
tmux capture-pane -t claude-session -p -S -5
```

**轮询效率原则：**

- **禁用 `sleep(10) * N` 长循环**。CC 可能在 15 秒内完成并返回 `❯`，你却还在 60 秒的第 5 轮里傻等。
- **短频快速**：每次轮询后立即检查停止信号。间隔不超过 5-8 秒，总次数不超过 8-10 次。
- **停止信号要全**：不仅是 `❯`，还包括 `Enter to select`、`Skip interview`、`Would you like to proceed`、`ready to execute`、`Claude has written up a plan`。
- **发现停止信号立即跳出**循环，不要再等下一轮。

## 4. 辩论协议

当 CC 输出需要校验或方案需要讨论时，Hermes 不直接转发，进入结构化辩论流程。

### 4.0 讨论模式（Collaborative Assessment）— 方案细化场景

**辩论协议 §4.1-4.7 适用于存在实质性分歧的场景。当目标是「逐项确认、达成共识、推进执行」时，改用讨论模式。**

适用场景：CC 产出分析报告/差异清单 → Hermes 审核后需要逐条确认是否执行、修正还是保留。双方立场不是对立而是协同。

**讨论模式工作流：**

```
CC 产出分析/方案
     │
     ▼
Hermes 独立评估每一条
     ├── 同意 → 给出确认 + 简要理由
     ├── 有异议 → 说明反对理由 + 建议方案
     └── 不确定 → 提出问题 + 请 CC 回应
     │
     ▼
Hermes 将评估逐条发回 CC（点对点）
     │
     ▼
CC 逐条回应（同意 / 修正 / 补充理由）
     │
     ▼
Hermes: 仍有分歧 → 升级到辩论协议 §4.1
Hermes: 全部共识 → 锁定方案 → 发出执行指令
     │
     ▼
汇报用户：讨论结论摘要（含 CC 的异议点如果存在）
```

**关键规则：**
- **独立评估优先**：每一条必须给出 Hermes 自己的判断，不能写「CC 的建议是 X，你怎么看？」——这是传话筒行为
- **点对点，不要打包**：每个差异点单独发回 CC，或者按主题分批次（每批 ≤5 条），让 CC 逐条回应。一次性把 12 条全部抛给 CC 后 CC 需要消化很久
- **有依据地同意/反对**：光说「我同意」不够——要带理由（「我同意删，因为计划明确砍除」）。光说「我不同意」也不够——要带替代方案
- **用户汇报规则**：Hermes 汇报用户时不能是「我跟 CC 讨论了，以下是我们的结论」——而应是锚定在用户关心的差异点上的结论摘要。例如：「对照 plan 发现 4 个文件需删除、路由路径需修正。我跟 CC 讨论后已确认删除清单和修正方案，正在执行」

**反面案例（2026-06-03）：** Hermes 用讨论模式与 CC 逐条确认了 12 项差异中的 #1-7，效果良好（CC 逐条回应、快速形成共识）。但汇报给用户时仍以「我跟 CC 讨论结论」开头——用户需要的是锚定在差异本身的结果：「删掉 5 个文件、拍平/修正路由、Tier矩阵最后补」。前一方式像聊天纪要，后一方式像执行简报。

**与辩论协议的关系：**
- 讨论模式是辩论协议的轻量变体：双方立场天然一致（都是优化方案），逐项确认而非争议裁决
- 发现实质分歧时，标注该条 → 进入辩论协议 R2 质询 → 裁决后回到讨论模式继续
- 讨论模式的输出格式与辩论协议的 CONSENSUS 格式一致

### 4.1 核心原则

- Hermes **不是** CC 和用户之间的消息传递员
- Hermes **是**辩论的主动参与者——分析 CC 的方案、找出漏洞和未考虑的点、提出质疑、推动方案完善
- 每轮从 CC 收到方案后，Hermes 必须先**独立分析**再决定下一步：有实质分歧→进入 R2 质询；无分歧→直接确认执行
- **禁止**：将 CC 的回复原封不动转发给用户而不加分析；用"CC 说了 X，你怎么看？"代替自己的判断

**反面案例（本次会话）：** CC 给出飞书表格方案后，Hermes 直接转发给用户说"CC 分析结论：..."。用户立即指出「你不是传话筒，你应该先判断这个方案有没有问题」。Hermes 后补的分析发现了 3 个问题：全 card 化会让短文变沉重、5 行表格限制是致命伤、CC 没读过 Hermes 代码。如果一开始就先独立分析，这些问题在第一次汇报时就会被指出。

**三层架构：**

```
Profile（方案层）         → 出方案，不关心本地环境
        │
        ▼
Claude Code（质疑层）     → 技术可行性校验，输出 verdict
        │
        ├── ACCEPT          → 直接执行
        ├── ACCEPT_WITH_NOTES → 微调后执行
        └── REJECT          → 上报 Hermes
                │
                ▼
        Hermes（裁决层）    → 最终决策，倾向采信 CC
```

### 4.2 风险分级

在裁决前先判定风险等级，决定处理路径：

| 分歧类型 | 风险等级 | 处理方式 |
|---------|---------|---------|
| **事实分歧** | — | 就近查证后以事实为准 |
| **判断分歧** | 低风险（不影响安全/文件稳定） | Hermes 拍板，CC 执行 |
| **判断分歧** | 高风险（涉及安全、删除/修改敏感文件、外部网络操作等） | Hermes 向用户汇报双方论点，由用户决定 |
| **不分歧** | — | 立即执行 |

**风险判定参考：**

| 低风险（Hermes 拍板）| 高风险（汇报用户） |
|---|---|
| 代码风格、命名规范 | git push / 部署操作 |
| 库/框架选择 | rm / 删除文件 |
| 文件组织结构 | curl 外部 URL / API 调用 |
| 工具参数选项 | 修改系统配置（sshd、防火墙等） |
| 日志级别、超时设置 | 涉及权限变更 / 安全策略 |

### 4.3 查证分工

辩论中出现不确定事实时，按分工查证，不猜测：

| 查证方 | 适用场景 | 示例 |
|--------|----------|------|
| CC 自查 | 本地 Windows 文件、工具版本、项目代码 | "你确认 sshd_config 里 Port 是 22 吗？直接读一下" |
| Hermes 查证 | 云端状态、网络搜索、公开文档 | "这个 npm 包的最新版本号是？我搜一下" |

**铁律：不确定先查不猜。** 查不到就标注「未验证」而非假设。双方都无法查证→如实告知用户"无法确认"，不编造。

### 4.4 R2 子轮机制

R2 质询轮最多 3 子轮，超限强制进 R3：

| 子轮 | 做什么 | 限制 |
|------|--------|------|
| R2a | Hermes 一次性列出所有问题 → CC 逐条回应 | 必须一次性列完，只回应分歧点不重述 |
| R2b | Hermes 追问「R2a 你说 X，查证一下」或「Y 点你漏了」 | 只能基于 R2a 回应，不能提全新问题 |
| R2c | 同上，仅限查证或补充 | 只能基于前两轮回应 |

- R2c 结束后**强制进入 R3**，无论是否还有异议
- **如果 R2 中确认无实质分歧 → 立即执行，跳过 R3**

### 4.5 Verdict 格式

CC 输出的结构化判定，Hermes 解析后决策：

```
VERDICT: ACCEPT | ACCEPT_WITH_NOTES | REJECT
CONCERNS:
  - [维度] 问题描述 → 建议修改
SUGGESTION: （可选）建议升级模型/拆分任务等
```

### 4.6 裁决原则

| 争议类型 | 倾向 | 理由 |
|----------|------|------|
| 技术可行性（路径、依赖） | 采信 CC | 执行层更懂本地环境 |
| 环境约束（磁盘、内存、锁定） | 采信 CC | 执行层直接感知 |
| 业务逻辑（需求理解、优先级） | 采信 Profile | 分析层更懂需求 |
| 成本/时间权衡 | Hermes 自行判断 | 调度层的核心职责 |

**终局规则：**
- **事实分歧**：就近查证后以事实为准
- **判断分歧 · 低风险**：Hermes 裁决
- **判断分歧 · 高风险**：Hermes 汇总双方论点汇报用户，由用户决定
- **僵局**：R3 后仍无法达成一致 → 汇报用户

### 4.7 Token 节省规则

1. CC 每轮**只回应分歧点**，不重述已达成一致的部分
2. Hermes 预筛选——不提出不影响最终结论的细枝末节
3. 使用结构化格式：「已同意：X。分歧：Y，原因是 Z」
4. Hermes 提问时应包含：当前环境上下文、具体问题、期望输出格式、（可选）已知约束

## 5. 任务类型专用流程

### 5.1 验证 / 复杂问题

```
R1 分析轮
  ├── Hermes 提明确问题，附带上下文（Tailscale 状态、环境限制等）
```

### 5.2 写作 / 协作类

**禁止直接让 CC 写正文**——必须先走「方案→审核→执行」三步：

**反面案例：** Hermes 直接发全文写作指令让 CC 执行，结果架构方向完全反了。如果先出方案，方向错误在 R0 就被拦截。

## 7. 增强 ACK 指纹协议（v3.1）

*2026-06-02 Hermes×CC 辩论产出。解决 send-keys 截断的可靠检测问题。*

### 7.1 核心设计：分离回显与判断

CC 在 ACK 中**只回显事实，不做判断**。截断判定完全由 Hermes 侧负责。

```
CC 侧（回显事实）                    Hermes 侧（做判断）
     │                                      │
     ├─ 提取 task_id, step, done            ├─ 比对：期望值 vs 实际回显
     ├─ 回显关键摘要                        ├─ 不一致 → 判定截断 → 重发
     └─ 标注 SUSPECTED 信号（可选）         └─ 一致 → 确认送达 → 继续监控
```

**为什么 CC 不做判断**：CC 在 plan mode 下接收消息时，消息是作为"上下文"理解的，CC 可能无法可靠判断消息是否截断。由 Hermes（消息的发送方）比对指纹更准确。

### 7.2 ACK 格式

```markdown
<!-- ACK:task-X:step-3 -->
  复述: <任务摘要>
  校验: [task_id=task-X, step=3, total=5, done=2]
  指令完整性: OK / SUSPECTED_TRUNCATION
  [state: id=task-X step=3/5 done=2 ctx=摘要]
```

Hermes 收到 ACK 后：
1. 比对 `task_id`、`step`、`total`、`done` 与发送时是否一致
2. 检查"复述"摘要是否与指令内容匹配
3. 不一致 → 判定为截断 → 重新发送指令

### 7.3 截断检测信号（CC 侧可标注）

| # | 检测信号 | 示例 |
|---|---------|------|
| 1 | 开标记 `<!-- TASK:task-X:step-N -->` 存在但无闭合内容 | 收到标记后消息就结束了 |
| 2 | `[state]` 行的 step 与标记中的 step 不一致 | 标记 step=3 但 state step=2 |
| 3 | `[state]` 行中的 done > step | done=4 但 step=3 |
| 4 | 指令在句子中间突然结束 | "请执行以下操作：先读取"（无后续） |

### 7.4 "步"的粒度重定义

辩论产出：**步 = Hermes 指令条数，不是 CC 操作数。**

| 旧定义（模糊） | 新定义（明确） |
|---------------|---------------|
| 一条指令 ≤5 个步骤，但"步骤"未定义 | 一个 task 最多 3 条 Hermes 指令 |

**实际效果**：一条 Hermes 指令内，CC 可以自主执行多个操作（读取→编辑→验证），这些算 1 步内的子操作，不占步数配额。

```
# task-X: 批量修改 5 个文件 + 运行测试

Hermes → CC: 指令1 (step 1/3): "修改 a.js, b.ts, c.py 中的 XXX 配置项"
  CC 内部: 读取3个文件 → 编辑3个文件 → 逐个Read验证 → 返回 DONE
  (1条指令，CC内部多操作，步数=1)

Hermes → CC: 指令2 (step 2/3): "修改 d.json, e.yaml 中的 YYY 配置项"
  (步数=2)

Hermes → CC: 指令3 (step 3/3): "运行测试并确认全部通过"
  (步数=3)
```

### 7.5 权限预授权共识

辩论产出——仅保留一条预授权规则，其余全部弹窗：

```json
// .claude/settings.local.json 中仅新增：
{
  "permissions": {
    "allow": [
      "Bash(git *):allow"
    ]
  }
}
```

| 命令 | 决策 | 理由 |
|------|------|------|
| `Bash(git *):allow` | ✅ 预授权 | 协作最高频操作，git 有 reflog 兜底 |
| `Bash(cp *):allow` | ❌ 弹窗 | 可复制敏感文件到任意位置 |
| `Bash(mv *):allow` | ❌ 弹窗 | 可移动/覆盖系统文件 |
| `Bash(python *):allow` | ❌ 弹窗 | 任意代码执行，信任边界不同 |
| `Bash(node *):allow` | ❌ 弹窗 | 同上 |

### 7.6 完整的协作优化优先级

| # | 项目 | 优先级 | 涉及方 | 行动 |
|---|------|--------|--------|------|
| 1 | 截断检测：ACK 指纹回显 | P0 | CC + Hermes | CC 回显指纹，Hermes 比对判定 |
| 2 | 短链路：≤3 条 Hermes 指令 | P0 | CC + Hermes | 行为守则 #2 从 ≤5 改为 ≤3 |
| 3 | 超时重发：30s 无 ACK/DONE | P1 | Hermes | 30s 超时自动重发 |
| 4 | 权限预授权：仅 git | P1 | CC 本地配置 | settings.local.json 加一条规则 |
| 5 | DONE 结构化 | 降级 | — | 正则提取够用，暂不改动 |

## 8. PAUSE 处理（v2.1 新增）

CC 遇到需要 Hermes 决策的边界情况时发送 `<!-- PAUSE:task-X:step-N -->`，携带 `reason` + `suggested`。PAUSE 后 CC 停止执行等指令。

**Hermes 四种响应方式：**

| 响应 | 含义 | 使用场景 |
|------|------|---------|
| `RETRY` | 重试当前步 | CC 判断错误可重试修正 |
| `ABORT` | 终止整个 task | 无法继续，触发回滚讨论 |
| `CONTINUE` | 按 CC 建议方向继续 | 同意 CC 的 suggested 方案 |
| `PAUSE-ACK` | 收到暂停，稍后回复 | 需要向用户请示后再决策 |

**处理流程：**
1. capture-pane 检测到 `<!-- PAUSE:... -->` → 立即停止轮询
2. 读取 CC 的 reason + suggested
3. Hermes 判断或请示用户后，发送对应响应
4. CONTINUE/RETRY → 继续监控；ABORT → 进入回滚讨论

**重要**：PAUSE 不可被忽略——CC 在 PAUSE 状态下不会继续执行，必须收到 Hermes 响应后才能推进。

## 9. DISCUSS 队列拦截（v3.8 新增）

**场景**：CC 在 accept edits 模式下生成自动建议（`> 开始写 P1 代码`），会优先执行自动建议而忽略排队的 `[HERMES:DISCUSS]` 消息。

**识别信号**：
- capture-pane 中看到 CC 执行工具调用（● Bash/Read/Edit 等）
- 同时底部出现 `Press up to edit queued messages` → 说明 DISCUSS 在排队
- 自动建议以 `>` 开头，内容为 CC 口吻描述下一步操作

**处理**：立即 `C-c` 打断。DISCUSS 已在输入队列中，打断后 CC 自动处理下一条消息即 DISCUSS，**无需重发**。

**反面案例（2026-06-02）**：CC 未处理 DISCUSS 前在错误方向浪费 1m34s + 多轮弹窗，写了 3 个有误文件。打断后 DISCUSS 自动接管，CC 重新评估，修正了所有错误。

**判断原则**：只要 CC 在执行操作时 DISCUSS 排队中，必打断。宁可误打断（无损失）不可漏打断（浪费 token + 出方向性错误）。

## 9.5 send-keys 消息排队现象（2026-06-10 实战）

**场景**：在 accept edits 模式下，通过 tmux send-keys 发送的多条指令可能出现在 CC 的输入框中但 CC 不会自动拾取处理。

**典型表现**：
- send-keys 后指令出现在输入框中，但 CC 仍显示空闲（❯），不开始处理
- 连续发送多条 send-keys 时，所有消息排队在输入框中等待
- 有时单独按 Enter 可以触发 CC 处理队首消息，有时 Enter 也被吞

**已知触发条件**：
- CC 刚完成一轮回复后（accept edits 模式切换的间隙期）
- 多条 send-keys 快速连续发送时

**处理方式**：
- 发送指令后等待 3-5 秒确认 CC 是否开始处理（出现 emoji thinking 标记）
- 如果消息在输入框排队但 CC 不处理 → 尝试单独按 Enter
- 如果 Enter 也无效 → CC 可能已进入 Phase 2/3 阻塞（见 error-recovery.md §10）

**预防**：每条指令发送后确认 CC 已开始处理（capture-pane 看到思考 emoji）再发下一条。不要连续快速发送多条 send-keys。

## 10. 自言自语监控模式（2026-06-24 新增）

**场景**：Hermes 通过 tmux capture-pane 监控用户与 CC 的实时讨论。用户可能在 tmux session 中 attach 并直接与 CC 交互，Hermes 通过轮询 pane 内容观察对话进展。

**核心规则**：

1. **用 💭/⚠️/📋 前缀做自言自语**：发现 CC 回复有问题、用户在讨论中 @ Hermes 征求意见等场景时，通过自言自语（💭/⚠️/📋 前缀）在 Hermes 自身的回复中记录分析和质疑，**不直接回复用户**
2. **不主动输出**：除非用户显式 @ Hermes 或说 "OK" 要求汇报，否则 Hermes 保持静默监控，用工具调用的 process 日志记录观察
3. **等用户说 OK 才结束监控 turn**：用户说 "OK" 或 "汇报" 后，Hermes 汇报本轮监控的所有自言自语记录和发现的问题
4. **轮询节奏**：与正常监控相同（5-8s 间隔，短频快速），但 turn 内可以发多轮 capture-pane 不输出到用户

**典型模式**：
```
Hermes: [启动监控，turn 不结束]
  → capture-pane → 发现 CC 回复
  → 💭 CC 提出了方案 C，倾向于 XXX。质疑：...
  → capture-pane → 用户输入
  → ⚠️ 用户在讨论 @ 语法归属问题，未@
  → capture-pane → 无变化
  → 📋 用户没输入，可能在思考。继续监控。
  → capture-pane → 用户说 "OK"
  → 结束 turn，汇报自言自语汇总
```

**与普通监控模式的区别**：
- 普通监控：Hermes 是 CC 的指令者，发指令→等结果→汇报
- 自言自语监控：Hermes 是**观察者**，不向 CC 发指令，只记录观察和分析；用户是 CC 的直接交互者

**⚠️ 注意**：此模式与 pitfall #102（CC 观察监控模式）有重叠但不同——#102 是用户手动操作 CC 时 Hermes 做基础设施搭建+观察；自言自语模式侧重于用户与 CC 讨论方案时 Hermes 的旁听和分析记录。

## 11. COMPLETE 标记（v2.1 新增）

task 所有步骤执行完毕后，**由 Hermes 发送** `<!-- COMPLETE:task-X -->`，CC 回复确认。双方都知道 task 结束。

**为什么需要 COMPLETE：** 之前 task 结束靠「没有新指令」判断，这与「指令丢失/截断」无法区分。COMPLETE 提供了明确的 task 边界信号。

**注意**：COMPLETE 是 Hermes 发的输入标记，不是 CC 的输出标记。CC 不应主动发送 COMPLETE。
